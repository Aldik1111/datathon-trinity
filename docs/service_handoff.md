# Участник 3: контракт и передача команде

Эта ветка основана на новом клоне очищенного main. Старые ветки/коммиты не сливать.
Прежний ZIP и все производные от него запрещены. Использовать можно только
синтетические материалы; новые реальные данные требуют отдельного разрешения.

## Что работает

- POST `/api/v1/analyze`: `.mov` в multipart-поле `file`, ответ 202 с job_id,
  status=processing и demo. Обязателен `X-API-Key`.
- GET `/api/v1/jobs/{job_id}`: processing/done/failed, тот же ключ. Неизвестный
  или истёкший job_id — 404; неверный ключ — 401. Ограничение файла — 413,
  расширения — 415, пустого файла — 400, очереди — 503.
- Ошибка/отсутствие модели: failed с безопасным сообщением, без verdict.
- Очередь и SQLite рассчитаны на один API-процесс. Бюджет анализа включает
  ожидание очереди, декодирование и загрузку модели. Максимальная настройка 300 с.
- Каждый анализ запускается через spawn в отдельном процессе, завершается при
  тайм-ауте или остановке сервера. Результат передаётся ограниченным локальным
  временным JSON, чтобы блокирующее чтение pipe не нарушало контроль тайм-аута.
- Видео удаляется после результата/ошибки; промежуточный worker JSON — всегда.
  При запуске в выделенном UPLOAD_DIR очищаются оставшиеся с аварии UUID.mov и
  UUID.worker.json. Не используйте UPLOAD_DIR для пользовательских оригиналов.
- Результаты с JPEG удаляются по JOB_TTL_SEC, SQLite secure_delete включён.
  Это не гарантирует стирание резервных копий или остаточных блоков файловой системы.

## Итоговый ответ

```json
{
  "job_id": "generated-id",
  "status": "done",
  "verdict": "violation",
  "violations": [{
    "type": "Название события",
    "timecode_sec": 0.4,
    "description": "Наблюдаемое действие",
    "evidence_frames": [{"timestamp_sec": 0.4, "image_base64": "JPEG_BASE64"}],
    "rule": null,
    "rule_status": "unverified"
  }],
  "demo": true
}
```

Это схема, не результат распознавания. Отрицательный ответ содержит
`verdict=no_violation` и `violations=[]`. Demo отмечен в POST/GET, названии и
описании события, предупреждении и заголовке результата UI. В real отсутствующий
анализатор даёт ошибку, постоянный вердикт не подставляется.

## Что получить от участника 2

`analyze_video(video_path)` должен вернуть `AnalysisResult` из
`src/vision/contracts.py` (или словарь с теми же полями). Сигнатура не менялась.
Event: event_type, timecode_sec, description, evidence_frames, необязательный rule_id.
EvidenceFrame: timestamp_sec и настоящие jpeg_bytes. На событие 1–3 кадра,
не более 4 MiB каждый и 12 MiB суммарных JPEG на результат. Типы и rule_id должны
совпадать с согласованными правилами. Не возвращать no_violation при исключении.

Нужны код, перечень локальных зависимостей, разрешённые веса и их лицензии,
инструкция подготовки и ограничения. MODEL_PATH передаётся через окружение.
Загрузка модели входит в бюджет каждого нового процесса. Во время анализа
нет загрузок весов, облачных AI-запросов или идентификации лиц.
До разрешения новых данных — только синтетические тестовые анализаторы.

## Что получить от участника 1

Схемы разметки и предсказаний, согласованные типы событий и проверенный реестр
нормативных оснований РК. Предыдущие таблицы и результаты восстанавливать нельзя.
Для каждой новой записи `configs/rules.json` нужны rule_id, title, url (HTTPS),
section, checked_at, limitations и verified=true только после реальной проверки.
Сейчас реестр пуст. Адаптер не берёт нормативные ссылки из ответа модели, а
сопоставляет rule_id с этим реестром. UI требует rule_status=verified для показа
подтверждённого источника; в остальных случаях явно показывает отсутствие основания.

## Что остаётся участнику 3

Подключить отдельно разрешённый реальный анализатор и новые проверенные правила,
повторить интеграционные тесты, измерить реальные сроки и передать предсказания
на оценку. Затем согласовать среду публикации и выполнить внешний приёмочный
сценарий. Конфигурация подготовлена в [deployment.md](deployment.md).
Технические тесты не доказывают качество распознавания или корректность правовой связи.
