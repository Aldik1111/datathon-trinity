# Состояние проекта после аудита — 18 октября 2026

Сервис технически проверен. Надёжное распознавание нарушений пока не подтверждено.
Этот документ описывает выполненную работу и её ограничения. Частные результаты
по отдельным видео, разметка, веса и локальные настройки в репозиторий не входят.

## Что сделано

1. Проверено актуальное состояние репозитория и подготовлено отдельное окружение.
   Основа аудита — опубликованный коммит `0f15815` ветки
   `feature/local-safe-recognition`. Основные изменения аудита — коммит `19f0ca6`.
2. Исправлена маршрутизация API. Поле `analysis_type` и настройка
   `DEFAULT_ANALYSIS_TYPE` определяют выбор между контрактом жюри, анализом
   состояния сейфа и экспериментальными сценариями. Старые настройки сохраняют
   предусмотренную совместимость. Добавлен защищённый маршрут готовности
   `/api/v1/readiness`.
3. Экспериментальные ответы не превращаются автоматически в подтверждённые
   нарушения или в утверждение, что нарушений нет. Несовместимый анализатор
   отклоняется для контракта жюри; отсутствие модели не подменяется успешным ответом.
   Интерфейс показывает эти ограничения.
4. Добавлен явный учёт неподдерживаемых классов. В новой политике поддержки для
   класса нужны как минимум две независимые положительные группы видео и одна
   отрицательная. Это условие запуска эксперимента, а не гарантия качества.
5. Обучены две отдельные экспериментальные версии. Первая применяет новую
   политику поддержки; вторая дополнительно вычитает типичный для клипа признак,
   чтобы уменьшить влияние его неизменной части. Исходная модель сохранена.
6. Подготовлены команды проверки целостности передачи, извлечения признаков,
   обучения, сравнения версий и проверки через отдельный процесс API.
   Выходные файлы экспериментов сохраняются локально в исключённой из Git папке.
7. Составлены план уточнения разметки и обзор ограничений нормативных оснований.
   Проверенных правил для автоматической квалификации эпизодов пока нет.

## Что проверено

На исходном снимке кода прошли 185 тестов. После изменений полный локальный запуск
дал **209 passed, 1 warning, 2 subtests passed** за 15,94 секунды.
Предупреждение связано с устаревающим способом подключения HTTPX в Starlette;
ошибок тестов не было. Это результат локального запуска, а не статус GitHub Actions.

Тесты проверяют API, ключ доступа, очередь, ограничения загрузки, тайм-ауты,
очистку, формат ответа, интерфейс, политику поддержки классов и расчёт метрик.
Они используют искусственные изображения и синтетические видео, без частного
набора и обученных весов.

Отдельно проверен настоящий HTTP-путь: отдельный процесс сервера получил
синтетический MOV, выдал `job_id`, обработал задачу и вернул результат.
Проверены отказ без ключа, отказ для неверного расширения, статусы задачи,
удаление загруженного временного файла, JPEG-кадры там, где они возвращались,
и одинаковый результат при переименовании одного и того же видео.
Эта проверка использовала локальные веса исходной и второй экспериментальной
модели. Она подтверждает работу интеграции, но не качество распознавания.

## Что показали эксперименты

**Улучшение распознавания не подтверждено.** Ложные тревоги остаются частыми.
Ужесточение поддержки исключило редкие классы, в том числе нужный сценарий
«возврат денег». Уменьшение числа тревог при отключении классов нельзя считать
доказательством, что модель лучше распознаёт все необходимые события.

Сравнение выполнялось на известном наборе разработки с разделением целых групп
исходных видео. Дубликаты не разделялись между обучением и проверкой. Отдельного
нетронутого набора новых съёмок для окончательной проверки не было.
Часть причин в положительных эпизодах неизвестна; отсутствие метки не
использовалось как доказательство отсутствия соответствующего события.

Ни одна новая версия не выбрана для применения по умолчанию. Текущий сценарный
анализатор ищет кандидатов по признакам кадров; он ещё не реализует полноценную
цепочку «объекты → действия → порядок действий → нарушение». Возвращаемое окно
около пика оценки не является проверенной границей действия.

## Что нужно сделать дальше

1. Проверить разметку людьми: что именно видно, когда действие началось и
   закончилось, какие объекты участвовали и достаточно ли виден весь эпизод.
   Нормальное действие и отсутствие действия должны быть разными метками.
2. Добавить независимые примеры редких действий и похожие нормальные эпизоды.
   Сохранить отдельный набор новых съёмок для итоговой проверки.
3. Подготовить экспорт подтверждённых событий и связей с объектами. Поля
   `action_presence` и проверки вторым разметчиком пока описаны как план;
   в сайт разметки в рамках этого аудита они не добавлялись.
4. Построить и проверить распознавание объектов, состояний и действий, затем
   правила их последовательности. Невидимое действие должно оставаться
   неизвестным, если запись не позволяет проверить весь нужный интервал.
5. Измерить по каждому классу пропуски, ложные тревоги и точность времени на
   отложенных съёмках. Только после этого выбирать рабочую модель и пороги.
6. Проверить применимость конкретных внутренних правил отдельно от визуальных
   наблюдений, прежде чем выдавать подтверждённую квалификацию нарушения.
